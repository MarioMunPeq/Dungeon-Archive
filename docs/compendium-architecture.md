# Compendium Architecture

## Overview

The Compendium is the read-only reference system for D&D 5e official content. It is **immutable** — user-generated content never mixes with official data. It is the single source of truth for rules; user data only stores references to it.

---

## Data Source

**5etools** is the source of truth for D&D 5e compendium data. It lives in `external/5etools/` as an immutable read-only dependency.

**Important:** 5etools data is never used directly at runtime. It is processed at build time into optimized static JSON under `src/generated/compendium/`.

---

## Categories

Exactly seven categories are shipped:

| Category    | Generated file       | Notes |
|-------------|----------------------|-------|
| Spell       | `spells.json`        | |
| Monster     | `monsters.json`      | |
| Equipment   | `equipment.json`     | |
| Condition   | `conditions.json`    | |
| Action      | `actions.json`       | |
| Magic Item  | `magic-items.json`   | |
| Feat        | `feats.json`         | |

The category registry (`src/compendium/category-registry.ts`) drives routes, search filters, and display metadata. Adding a category means adding its build transform, generated JSON, registry entry, and getters — not a redesign.

## Build-Time Processing

### Pipeline

```
external/5etools/ (read-only)
    ↓
scripts/compendium/
    ├── allowed-sources.ts         # Permitted sources
    ├── build.ts                   # Orchestration
    ├── entries.ts                 # Per-category entry generation
    ├── categories/{action,condition,equipment,feat,magic-item,monster,spell}/
    │                              #   transform + validate per category
    ├── id.ts                      # Canonical id generation
    ├── identity.ts                # Version/edition identity
    ├── generate-index.ts          # Search index
    ├── generate-related-index.ts  # Cross-entity relationships
    └── normalizer/                # Text normalization
    ↓
src/generated/compendium/
    ├── spells.json
    ├── monsters.json
    ├── equipment.json
    ├── conditions.json
    ├── actions.json
    ├── magic-items.json
    ├── feats.json
    ├── search-index.json
    ├── related-index.json
    └── manifest.json
```

Generated files are committed to Git and shipped with the app. They are regenerated by `pnpm build:compendium`.

## Runtime Architecture

```
src/generated/compendium/  (build pipeline output)
        ↓
loader.ts                  (async: imports all JSON, creates Maps + cached arrays)
        ↓
repository.ts              (sync: Map lookups, cached array getters)
search.ts                  (sync: substring search with scoring)
        ↓
index.ts                   (public API surface)
        ↓
React components           (import from @/compendium)
```

### Lifecycle

```
main.tsx
  → await loadCompendium()   // loads everything: entities + search index
  → React renders            // all data in memory, all access is synchronous
```

Single initialization. No partial states, no two-step setup. After startup, every read is a synchronous Map lookup.

### Public API

```typescript
await loadCompendium();                       // once, before render

getSpell(id)                                  // synchronous, null if not found
getCondition(id)
getEntity(category, id)
getSpells(): readonly Spell[]                 // cached arrays, zero allocation
getConditions(): readonly Condition[]
getEquipmentList(): readonly Equipment[]
getActions(): readonly Action[]
getMonsters(): readonly Monster[]
getMagicItems(): readonly MagicItem[]
getFeats(): readonly Feat[]

search(query): readonly SearchIndexEntry[]    // synchronous, sorted

resolveEntity(canonicalId)                    // id → entity
getVersions(entity)                           // 2014 vs 2024 editions
selectPreferredVersion(entity)                // best edition for the context
getRelatedEntities(entity)                    // cross-references
referenceToUrl(reference)
slugFromCanonicalId(canonicalId)
categoryLabel(category)
buildFilterDefs(category)                     // list-page filters
applyFilters(entities, filters)
toCardData(entity)                            // list-card display data
```

### Rules

- Components import from `@/compendium`, never from `@/generated/`.
- All data access goes through exported functions, never direct Map access.
- Initialization happens once, before React renders.
- Unknown IDs return `null`, never throw.
- Empty search returns `[]`.
- No runtime validation (that belongs to the build pipeline).

## Source and Edition Handling

`src/compendium/source.ts` models source codes (PHB, DMG, XGtE, ...) and editions. `scripts/compendium/identity.ts` (build side) relates 2014 and 2024 versions of the same entity; `getVersions` exposes them on entity detail, where the user picks the edition they play. `selectPreferredVersion` chooses a sensible default per category.

---

## Relationships

`related-index.json` is generated at build time and read through `src/compendium/relationships.ts`. `getRelatedEntities` returns entities that reference the current one and entities the current one references. Surfaces in the "Related" section of entity detail.

---

## Adding a New Category

1. Add the entity interface to `src/types/compendium.ts`.
2. Add it to the `EntityCategory` union.
3. Add its build transform under `scripts/compendium/categories/<category>/`.
4. Add its entry to `src/compendium/category-registry.ts`.
5. Add Map + cached array + getter to `src/compendium/repository.ts` and the `resolveMap` switch.
6. Add the dynamic import to `src/compendium/loader.ts`.
7. Add exports to `src/compendium/index.ts`.
8. Add route + filter definitions if the category should be browsable/filterable.

No changes to search, hooks, or component architecture.

---

## Validation

Validation happens in the build pipeline (`scripts/compendium/categories/*/validate.ts`): required fields present, types correct, no duplicate ids, search text normalized, index integrity. The runtime trusts build output and returns `null` for unknown ids.

---

## Non-Goals

- **No user-created Compendium entries.** Custom content is a permanent anti-feature.
- **No remote compendium updates.** Content ships with the app; new sources mean a new build.
- **No runtime network requests.** The Compendium is fully offline.
